### Step 3: Clean Parallel Build (4 Workers) (1:30 min)

1. **Action on Dashboard:**
   * Check **Clean Build**.
   * Select **Worker Limit: 4**.
   * Click **Run Build** *(or execute in terminal: `python cli.py build --workers 4 --clean`)*.
2. **Key Observations to Point Out:**
   * Watch all 4 library compilation units (`math`, `utils`, `stringops`, `fileio`) fire **simultaneously** in parallel.
   * Notice the metric card displays **Workers / Concurrency: 4 / 4**, recording **Peak: 4 active**.
   * The Task Table displays distinct assigned workers (`Worker 1`, `Worker 2`, `Worker 3`, `Worker 4`).
   * **Result:** The build completes in approximately **$2.075\text{ seconds}$**.
   * **Key Talking Point:** *"We achieved an empirical speedup of $2.36\times$, saving $2.825\text{ seconds}$ ($57.6\%$ reduction in build time). The reason it is not $4\times$ is Amdahl's Law: creating `libmylib.a` and linking `demo.exe` form a sequential critical path that cannot start until compilation finishes."*

### Step 6: Failure Propagation & Branch Isolation (1:30 min)

1. **Inject a Compilation Error:**
   In the second terminal, inject an intentional syntax error into `math.cpp`:
   ```powershell
   Set-Content "examples\cpp_demo\src\math.cpp" "#error Deliberate Demo Compilation Error`n"
   Get-Content "examples\cpp_demo\src\math.h" | Add-Content "examples\cpp_demo\src\math.cpp"
   ```
2. **Action on Dashboard:** Click **Run Build**.
3. **Key Observations to Point Out:**
   * `math.cpp.obj` turns **RED (FAILED)** with exit code 1.
   * Dependent tasks `libmylib.a`, `demo.exe`, and `test_runner.exe` turn **ORANGE (BLOCKED)**.
   * **Crucial Architectural Observation:** Independent compilation units `main.cpp.obj` still succeed! The engine does not crash or abort unblocked tasks.
   * Click on `math.cpp.obj` in the Inspector to show the captured compiler error output in the UI.
4. **Restore Clean File:**
   ```powershell
   git checkout -- examples/cpp_demo/src/math.cpp
   ```

## 3. Anticipated Professor Questions & Model Answers

### Q1: "Why did you build your own rebuilder instead of using file timestamps like Make?"
> **Answer:** *"Timestamps (`mtime`) have fundamental flaws: clock skew across network shares, timestamp clamping on FAT/NTFS filesystems, and false rebuilds when switching Git branches. In accordance with 'Build Systems à la Carte', we implemented a Verifying-Trace Rebuilder using SHA-256 hashing. We hash the command string, rule definition, input contents, and depfile headers. If the hashes match, the build is provably up-to-date, enabling reliable early cut-off."*

### Q2: "How do you track header file changes if they aren't declared in `build.ninja`?"
> **Answer:** *"CMake configures GCC with the `-MD -MT $out -MF $DEP_FILE` flags. When GCC compiles a source file, it emits a `.d` depfile listing all header files included directly or transitively. Our E2 rebuilder parses this depfile after compilation and incorporates the SHA-256 fingerprints of all included headers into the persistent build trace in SQLite."*

### Q3: "How do you guarantee that a task never starts before its dependencies finish?"
> **Answer:** *"E3 maintains an in-degree counter for every task in the dependency closure. A task's in-degree represents the exact count of unresolved explicit, implicit, and order-only dependencies. A task is only pushed to the `ready_queue` when its in-degree reaches 0. Furthermore, when tasks finish, we verified that the archive task `libmylib.a` start time ($t=3.7887\text{s}$) strictly exceeded the maximum finish time of all four object files ($t=3.7362\text{s}$)."*

### Q4: "Does your engine call `ninja.exe` under the hood?"
> **Answer:** *"No. We only use CMake with the `-G Ninja` generator to produce the initial `build.ninja` manifest. Our Python engine implements the lexer, parser, graph generator, scheduler, and subprocess executor completely from scratch. `ninja.exe` is never installed or executed."*

### Q5: "How does the live dashboard update without polling?"
> **Answer:** *"E4 utilizes a reactive publish/subscribe `EventBus`. When the scheduler transitions a task, it dispatches a typed `TelemetryEvent`. The FastAPI backend streams this event over a persistent WebSocket (`/ws/telemetry`) directly to the browser. The browser's vanilla JavaScript controller receives the JSON event and updates the SVG node class and metrics dynamically."*
